# decisions.md — 設計判断の記録(ADR)

意思決定を一つずつ記録する。**一度決めたら消さない**。覆すときは新しいADRを追記し、旧ADRに「Superseded by ADR-xxx」と印を付ける。他エージェントは「なぜこうなっているか」をここで確認し、蒸し返す前にまずここを読む。

書式: 状態 / 文脈 / 決定 / 根拠 / 影響。

---

## ADR-001: 製品の核は「ホスト型セッション遠隔操作」に置く
- 状態: 採択(2026-07-18)
- 文脈: Agent Manager 直接操作は非公式で壊れやすい。何を製品価値の中心に据えるか。
- 決定: node-pty でホストするターミナルセッション(Claude Code CLI 等)の遠隔操作を核とする。Agent Manager 連携は付加価値。
- 根拠: 標準 Extension API のみで完結し、Antigravity のバージョン更新に強い([findings.md](./findings.md) F1)。
- 影響: フェーズ0の最優先は node-pty 中継の縦切り。

## ADR-002: 転送路は P2P ではなくリレー+アプリ層E2EE
- 状態: 採択(2026-07-18)
- 文脈: 「P2Pで安全にできないか」という提案。WebRTC(DTLS)は経路E2EEが得られる。
- 決定: **P2Pは不採用**。Cloudflare 等のリレー+アプリ層E2EE(libsodium)を採用。
- 根拠:
  1. モバイル回線のNAT越えに TURN(実質リレー)がほぼ必須で「完全サーバーレス」にならない。
  2. 遠隔操作で守るべきは「勝手に承認/実行されない」= **ホスト側の認可**であり、転送路の選択では守れない。
  3. アプリ層E2EEでもゼロナレッジ中継は達成でき、運用・コストが読める(NFR-6)。
- 影響: リレー実装が必須成果物。E2EE鍵交換はペアリング時(QRに公開鍵)。

## ADR-003: Agent Manager 操作は「内部コマンド経由」で実験的に提供
- 状態: 採択(2026-07-18)。v0.1 の「操作は不可・スコープ外」を **supersede**。
- 文脈: [findings.md](./findings.md) F3 で操作系の内部VS Codeコマンド(`antigravity.sendPromptToAgentPanel` 等)が登録済みと判明。
- 決定: 相棒拡張から `vscode.commands.executeCommand` で内部コマンドを呼ぶ方式を第一候補に採用。DB直書き・language_server 直叩き(F4)は採らない。既定オフの**実験的機能**とする。
- 根拠: 正規のコマンド経路で副作用が少なく、DB破損リスクを回避。ただし引数未実測・バージョン依存のため実験扱い。
- 影響: フェーズ0で引数シグネチャを実測(TASK-05)。UIに「実験的・更新で停止しうる」を明示。機能検出してから使う(NFR-7)。

## ADR-004: 共有情報は個人メモリではなくリポジトリの docs/ に置く
- 状態: 採択(2026-07-18)
- 文脈: 複数のAIエージェントで共同開発する。情報共有と進捗共有の基盤が要る。
- 決定: 真実の情報源は **git リポジトリの `docs/`**(requirements / findings / decisions / tasks / collaboration)。各エージェントの私的メモリには共有前提の情報を置かない。
- 根拠: エージェント間でメモリは共有されない。git なら差分・履歴・レビューが可能。
- 影響: 進捗は tasks.md 更新+コミットで共有。作業ルールは collaboration.md に従う。

## ADR-005: マルチセッションは「ホスト側多重化+sessionId」で実現(リレーはセッション非解釈)
- 状態: 採択(2026-07-18)。requirements v0.3 で追加。
- 文脈: 1台のAntigravity上で複数セッション(複数の pty + 複数の Gemini 会話)をスマホから一覧・切替・並行操作したい。差別化の中核。
- 決定:
  1. **ホスト拡張がセッションを多重化**する。SessionManager が各セッション(pty/agent)を保持し、全メッセージに `sessionId` を付す。1本のリレー接続(WSS)で全セッションを収容する(セッションごとに接続を張らない)。
  2. **リレーはセッションを解釈しない**。ホスト⇄そのクライアント群を中継するだけで、`sessionId` を含む payload は E2EE のまま素通し(ADR-002 のゼロナレッジを維持)。
  3. クライアントは `sessions` メタ一覧を常時同期し、表示中セッションを subscribe。非表示セッションはホスト側 scrollback に蓄積し再購読時に再送(NFR-8 のため間引き方針は未決)。
- 根拠: 接続を1本に保つとペアリング/E2EE/再接続の管理が単純。多重化をホストに寄せることでリレーは汎用中継のままスケールし、ゼロナレッジも崩れない。node-pty は複数 spawn 可能で pty 並行は自然。
- 影響: protocol.ts に `sessionId` と制御メッセージ(session.list/create/close/subscribe/snapshot)を追加。リレーは payload 不透明のまま。UI にセッション一覧・個別ビューを新設(FR-3)。フェーズ0の 1:1 リレーはこの多重化に置き換える。
- 代替案: セッションごとに別WSS接続 → 却下(ペアリング/鍵/再接続が N 倍複雑、リレー側の相関管理も増える)。

## ADR-006: 配布は「PC拡張(Open VSX)+ スマホPWA + Android TWA」、iOSは後追い
- 状態: 採択(2026-07-23)
- 文脈: プロダクト化にあたり配布形態を決める。「拡張 vs アプリ」は二者択一ではなく、PC側=拡張(IDE内でnode-pty起動のため必須)、スマホ側=クライアントUI(現状PWA)という別部品。
- 決定:
  1. **PC側は Antigravity/VS Code 拡張**として Open VSX で配布(確定・代替不可)。
  2. **スマホ側は PWA を唯一の本体**とし、そのコードベースを使い回す。
  3. **Android は TWA(Bubblewrap)で PWA を包み Play Store 配布**(発見性・信頼感・通知安定・ストア課金)。
  4. **iOS は当面 PWA(ホーム追加)**。App Store ラッパーは需要が見えてから後追い(Apple審査・$99/年の壁を回避)。
- 根拠: 1つのWeb資産(PWA)を全プラットフォームで共有でき、TWAは薄いラッパーのため両立コストが最小。iOSラッパーは費用対効果が見えてからで十分。
- 影響(作業項目): (a)拡張のOpenVSX公開整備(publisher/manifest/README/アイコン/CDN自己ホスト済), (b)PWAの公開品質化(オフライン/アイコン/manifest整備), (c)TWA化(Bubblewrap, Digital Asset Links, 署名), (d)ストア掲載物(説明/スクショ/プライバシー)。iOSは保留項目として残す。

## ADR-007: 課金モデル(詳細は非公開)
- 状態: 採択(2026-07-23)
- 公開部分: **オープンコア**。拡張・スマホクライアント・リレー実装はOSS(MIT)として公開し、誰でも自前のリレーを立てて無料で使い切れる。将来、任意で使えるマネージドなホスティングと上位機能(複数PCの束ね、チーム/権限など)を提供する可能性がある。
- 価格・原価試算・競合分析を含む詳細は事業判断のため非公開(リポジトリ外で管理)。

## ADR-008: 既定でマネージドリレーを提供する(セルフホストは一級のまま)
- 状態: 採択(2026-07-26)
- 文脈: v0.1.0 公開時点では、利用者が自分で Cloudflare にリレーをデプロイしないと**何も動かなかった**。Cloudflareアカウント作成→OAuth→デプロイ→URLを設定、という手順は開発者向けツールとしても重く、採用の最大の障壁だった。
- 決定:
  1. **既定を本プロジェクト運営のマネージドリレー**(`wss://relay.termhop.dev`)にし、インストール直後にペアリングできる状態にする。スマホPWAは `https://termhop.dev`。
  2. **セルフホストは一級の利用方法として維持**する(MITのまま、README/PRIVACYに明記、設定を空にすると既定へ戻る)。
  3. 独自ドメインを取得する。既定URLは**一度出荷すると変更できない**(旧バージョンが見続ける)ため、将来リレーを別基盤へ移してもURLを維持できることを優先した。
- 根拠: 通信は**アプリ層E2EE**なので、他人のリレーを経由しても運営者に中身は読めない。「マネージドの手軽さ」と「信頼」を両立できるのはこの設計だから。ngrok/Tailscale と同じオープンコアの形。
- 影響: 運営者としての責任が発生 → `TERMS.md`(無保証・禁止事項)新設、`PRIVACY.md` を運営者視点に改訂。費用は月$5+従量(ADR-007の試算内)。可用性SLAは掲げない。
- 却下した案: 「セットアップを極限まで簡単にする」だけの案(Deployボタン等)。アカウント作成という不可避の手順が残り、ADR-007の無料枠(マネージド前提)とも整合しない。

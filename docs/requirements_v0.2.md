## 1. 背景と目的

Claude Code には、ローカルで動くセッションを外出先のスマホ・ブラウザから継続操作できる **Remote Control** 機能がある(アウトバウンドHTTPSのみでリレーサーバに接続する構成)。Antigravity IDE には相当機能がない。

本プロジェクトは、**Antigravity 上のエージェント作業を、外出先のスマホのブラウザから閲覧・継続・操作できる機能**を拡張機能として実現し、一般公開(プロダクト化)することを目的とする。

## 2. 用語

| 用語 | 意味 |
|---|---|
| ホスト | Antigravity が動作するローカルマシン+本拡張機能 |
| リモートクライアント | スマホ等のブラウザで開く操作用 Web UI(PWA) |
| リレー | ホストとリモートクライアントを仲介するクラウドサーバ。両者ともアウトバウンド接続のみ |
| Agent Manager | Antigravity 標準の Gemini エージェント機能(内部名 jetski / cascade) |
| ホスト型セッション | 本拡張機能が node-pty 等で自前にホストするターミナルセッション(Claude Code CLI 等) |
| 内部コマンド | Antigravity が登録している VS Code コマンド(`antigravity.*`)。相棒拡張から `executeCommand` で呼べる |

## 3. 実現可能性(v0.2 での確定・更新)

根拠の詳細は [findings.md](./findings.md)。

| # | 対象 | v0.1 判定 | **v0.2 判定** | 方式 |
|---|---|---|---|---|
| A | ホスト型セッション(Claude Code 等)の遠隔操作 | ◎ | ◎ | node-pty で PTY をホストし入出力をリレー中継 |
| B | Agent Manager 会話の**閲覧**ミラー | ○ | ○ | 会話DB(SQLite)を read-only 監視して差分配信(ベストエフォート) |
| C | Agent Manager への**入力送信・承認** | ✕ 不可 | **△ 実験的に可能** | 相棒拡張から内部コマンド `antigravity.sendPromptToAgentPanel` / `antigravity.command.accept` 等を `executeCommand` |
| D | claude.ai 公式リレーの流用 | ✕ | ✕ | 非公開。自前リレー必須 |

**C の格上げ理由**: Antigravity 本体バンドル(v1.107.0)に操作系の VS Code コマンドが登録済みであることを確認。DB直書き(破損リスク)や非公開HTTP APIを使わずに、同ウィンドウ内の相棒拡張から正規のコマンド経路で注入できる見込み。ただし**引数仕様は未実測**であり、バージョン更新で改名・削除され得るため「実験的」に留める。

**結論: 実現可能。** 製品の核は「ホスト型セッションの遠隔操作(A)」+「Agent Manager の閲覧ミラー(B)」。Agent Manager の**操作(C)は実験的機能**として提供し、コア価値には依存させない。

## 4. スコープ

### 4.1 スコープ内(MVP)
1. ペアリング(QR/URL 発行+鍵交換によるE2EE)
2. ホスト型セッションの遠隔操作(入力・出力閲覧・許可プロンプト応答)
3. Agent Manager 会話ミラー(read-only)
4. セッション一覧(切替・新規・終了)
5. 通知(Web Push)

### 4.2 スコープ内(実験的・フラグ制)
6. **Agent Manager 操作**: 内部コマンド経由でプロンプト送信・編集/コマンドの承認/却下。既定オフ、明示オプトイン、UI に「実験的・Antigravity更新で停止しうる」と明示

### 4.3 スコープ外
- スマホネイティブアプリ(PWAで代替)
- 画面共有型リモートデスクトップ(テキスト/構造化データ中継のみ)
- language_server 低レイヤーAPIの直接利用(Cの代替手段として調査はするが第一候補にしない)

## 5. システム構成

```
[Antigravity IDE]                        [クラウド]              [スマホ]
 拡張機能 (ホスト) ──outbound WSS──▶  リレー(E2EE中継)  ◀──WSS──  PWA
  ├ node-pty セッション管理            └ ペアリング仲介・中継のみ    ├ xterm.js ターミナルUI
  ├ 会話DBウォッチャ (read-only)          (ゼロナレッジ)             ├ 会話ミラービュー
  ├ 内部コマンドブリッジ (executeCommand)                           ├ エージェント操作UI(実験)
  └ E2EE 端点                                                       └ E2EE 端点
```

- ホスト・クライアントとも**アウトバウンド接続のみ**(ホスト側ポートを開けない)
- リレーは中継専用。**アプリ層E2EE でリレー運営者は内容を復号できない**

### 転送路の選定(P2P比較の結論)
WebRTC(P2P/DTLS)も検討したが、**モバイル回線のNAT越えにTURN(実質リレー)がほぼ必須**で「完全サーバーレス」にはならず、遠隔操作で守るべき認可はホスト側の責務で転送路では守れない。よって**リレー+アプリ層E2EE(libsodium)を採用**し、P2Pは不採用。詳細は [decisions.md](./decisions.md) の ADR-002。

### 技術スタック(想定)
| コンポーネント | 技術 |
|---|---|
| 拡張機能 | TypeScript / VS Code Extension API / node-pty / better-sqlite3(read-only) |
| リレー | Cloudflare Workers + Durable Objects(WSS中継)※常駐サーバと比較継続 |
| クライアント | PWA(TypeScript / xterm.js / Web Push / Service Worker) |
| E2EE | ペアリング時に鍵交換(QRに公開鍵)、libsodium |

## 6. 機能要件

### FR-1 ペアリング・認証
- FR-1.1 ワンタイムのペアリングQR/URL(有効期限付き)を発行
- FR-1.2 ペアリング時に鍵交換、以後E2EE
- FR-1.3 ペアリング済みデバイス一覧・個別失効(revoke)
- FR-1.4 全リモート接続を即時遮断できるキルスイッチ

### FR-2 ホスト型セッション遠隔操作
- FR-2.1 リモートから新規セッション作成(起動は拡張設定のプリセットのみ。任意コマンド不可)
- FR-2.2 入出力をリアルタイム双方向中継(目標レイテンシ体感1秒未満)
- FR-2.3 許可プロンプトにスマホから応答(キー入力中継で成立)
- FR-2.4 切断・再接続でセッション維持+スクロールバック再送
- FR-2.5 IDE側ターミナルビューでも同一セッションを閲覧

### FR-3 Agent Manager 会話ミラー(read-only)
- FR-3.1 会話DBを監視し新規ステップを差分配信
- FR-3.2 ユーザー発言/モデル出力/ツール呼び出し/サマリを区別表示
- FR-3.3 抽出失敗時は劣化表示(protobuf 非公開のため)、機能全体は落とさない
- FR-3.4 「閲覧のみ」を明示(操作は FR-6 で別途)

### FR-4 通知
- FR-4.1 ホスト型セッションが入力待ちで Web Push
- FR-4.2 Agent Manager 会話に新規ステップで通知(オン/オフ可)

### FR-5 一般公開・運用
- FR-5.1 Open VSX で公開(VS Code Marketplace は Antigravity から使えない)
- FR-5.2 リレーはマルチテナント、テナント間は暗号レベルで分離
- FR-5.3 匿名利用を基本(課金導入時に再検討)
- FR-5.4 利用規約・プライバシーポリシー。「ミラー(B)と操作(C)は非公式でありAntigravity更新で停止しうる」を明記

### FR-6 Agent Manager 操作(実験的)
- FR-6.1 既定オフの実験的機能フラグ。有効化はホスト側で明示操作を要する
- FR-6.2 内部コマンド経由でエージェントにプロンプト送信(`antigravity.sendPromptToAgentPanel` 等)
- FR-6.3 内部コマンド経由で編集/コマンドの承認・却下(`antigravity.command.accept` / `.reject` 等)
- FR-6.4 対応する内部コマンドが存在しない/失敗した場合は明確にエラー表示し、他機能に波及させない
- FR-6.5 リモートからの操作は監査ログに残し、レート制限を課す(NFR-2)

## 7. 非機能要件

| # | 要件 |
|---|---|
| NFR-1 | E2EE必須。リレーに平文を置かない。ホストはアウトバウンドのみ |
| NFR-2 | リモートに与える能力を最小化。ホスト型は起動プリセット制(FR-2.1)。Agent操作(FR-6)は既定オフ・監査ログ・レート制限 |
| NFR-3 | リレー障害時もローカル作業は無影響(拡張はリレー無しで無害に動作) |
| NFR-4 | 会話DB内容の外部送信はミラー/操作を明示有効化した場合のみ。既定オフ |
| NFR-5 | ホスト常駐処理(DB監視)は Antigravity 動作を阻害しない(read-only・WAL・ポーリング間隔管理) |
| NFR-6 | 個人開発で維持可能なリレー運用費(従量課金サーバレス第一候補) |
| NFR-7 | 内部コマンド依存部(FR-6, B)はバージョン耐性を考慮し、機能検出(存在確認)してから使う |

## 8. リスクと対応

| リスク | 影響 | 対応 |
|---|---|---|
| Antigravity のDBスキーマ/内部コマンド変更で B・C が壊れる | 中 | ベストエフォート/実験扱い(FR-3.3, FR-6.4, NFR-7)。コア価値は A に置く |
| 内部読み取り/内部コマンド利用の規約グレーさ | 中〜高 | ローカル処理・明示オプトイン。公開前に利用規約精査、必要なら実験フラグに隔離 |
| リモート承認開放による攻撃面拡大 | 高 | FR-6を既定オフ・監査ログ・レート制限。承認系は特に厳格な認可設計 |
| Anthropic/Google が公式同等機能を出す | 高 | 差別化は「Antigravityの複数セッション+Gemini会話をまとめて見て操作できる」点 |
| リレー悪用(不正中継/DoS) | 中 | ペアリング必須・レート制限・接続数上限。E2EEで踏み台価値を下げる |
| iOS SafariのWeb Push制約 | 低 | PWAホーム追加時のみ通知(iOS16.4+)。ガイドで案内 |

## 1. 背景と目的

Claude Code の Remote Control 相当を Antigravity 上に実現し、一般公開(プロダクト化)する。フェーズ0で「スマホ↔ローカルリレー↔PC上のPTY」の往復を実機で確認済み(F7)。フェーズ1では**外出先の回線から・安全に・複数セッションを**扱えるようにする。

**製品の差別化**: Claude Code 単体の Remote Control と違い、**1つのAntigravity環境で並行する複数の作業(複数のCLIセッション+複数のGeminiエージェント会話)を、スマホから一覧して切り替えながら操作できる**点に価値を置く。マルチセッションはこの差別化の中核。

## 2. 用語(v0.3 追加・更新)

| 用語 | 意味 |
|---|---|
| ホスト | Antigravity が動作するローカルマシン+本拡張機能。**複数セッションを束ねる単位** |
| セッション | 遠隔操作の対象となる作業単位。2種類ある(下記 kind) |
| kind = `pty` | 拡張が node-pty でホストするターミナルセッション(Claude Code CLI 等)。複数同時可 |
| kind = `agent` | Antigravity の Agent Manager(Gemini)会話。1会話=1セッション。閲覧(B)+実験操作(C) |
| sessionId | セッションの一意ID。全メッセージはこの ID で多重化される |
| リモートクライアント | スマホ等のブラウザで開く操作用 PWA。セッション一覧と個別ビューを持つ |
| リレー | ホスト⇄クライアントを仲介するクラウドサーバ。アウトバウンドのみ・ゼロナレッジ |
| ペアリング | ホストとクライアントを安全に紐付け、E2EE 鍵を確立する手続き |

## 3. マルチセッション・モデル(v0.3 の中心)

### 3.1 セッションの構造
各セッションは次のメタデータを持ち、ホストが真実源として管理する:
```
Session {
  id: string            // sessionId
  kind: "pty" | "agent"
  title: string         // 例 "claude: ~/work/foo", "Gemini: リファクタ相談"
  status: "running" | "waiting-input" | "idle" | "exited"
  createdAt: number
  preset?: string       // kind=pty のとき
  conversationId?: string // kind=agent のとき(会話DBの<id>)
}
```

### 3.2 多重化の考え方
- **ホストがセッションを多重化する**。1本のリレー接続(WSS)上で、全セッションのメッセージを `sessionId` で束ねて流す。リレーはセッションを解釈せず、ホスト⇄そのクライアント群の間を中継するだけ(ゼロナレッジ維持)。
- クライアントは「今表示中のセッション」を購読(subscribe)し、そのセッションの出力を受け取る。一覧表示のためにセッションメタデータ(`sessions` リスト)は常時同期する。
- kind=pty は複数を**並行実行**できる(バックグラウンドのセッションも動き続け、出力はホスト側 scrollback に蓄積、再購読時に再送)。
- kind=agent は会話DBの各会話に対応。ミラー(B)は read-only、操作(C)は実験フラグ時のみ。

### 3.3 UI(スマホ)
- **セッション一覧画面**: kind アイコン+title+status(入力待ちバッジ等)。タップで個別ビューへ。
- **個別ビュー**: pty は xterm.js 端末、agent はチャット風ミラー(+実験時は入力欄)。
- **新規作成**: pty セッションをプリセットから新規起動。戻る操作で一覧へ。
- バックグラウンドのセッションが `waiting-input` / 新規ステップになったら一覧にバッジ+通知。

## 4. 実現可能性(v0.3 時点)

| # | 対象 | 判定 | 備考 |
|---|---|---|---|
| A | ホスト型 pty セッション遠隔操作 | ◎ 実機確認済 | F7。フェーズ0で往復実証 |
| A' | pty の**複数同時**ホスト | ◎ 見込み高 | node-pty は複数 spawn 可。多重化はリレー/プロトコルに sessionId を導入するだけ |
| B | agent 会話の閲覧ミラー | ○ 非公式 | 会話DB(F2)監視。ベストエフォート |
| C | agent への入力・承認 | △ 実験的 | 内部コマンド(F3)経由。既定オフ |
| D | 公式リレー流用 | ✕ | 自前リレー必須 |

**結論: マルチセッション対応も実現可能。** 追加の技術的核心は「sessionId による多重化」と「セッション一覧UI」。

## 5. システム構成(v0.3)

```
[Antigravity IDE = 1ホスト]                 [クラウド]           [スマホ PWA]
 拡張機能
  ├ SessionManager ── pty#1 (claude)         リレー(E2EE中継)      一覧画面
  │              ├─ pty#2 (bash)     ──1本のWSSで──  ゼロナレッジ ──   ├ session购读/切替
  │              └─ agent#1 (Gemini会話) sessionIdで多重化  マルチテナント  └ 個別ビュー(端末/ミラー)
  ├ 会話DBウォッチャ(read-only)                                        通知(Web Push)
  ├ 内部コマンドブリッジ(実験)
  └ E2EE 端点 / ペアリング                                             E2EE 端点
```

### 技術スタック
| 層 | 技術 |
|---|---|
| 拡張 | TypeScript / VS Code API / node-pty / better-sqlite3(read-only) |
| リレー | Cloudflare Workers + Durable Objects(テナント=1つのDOに集約、WSS中継) |
| クライアント | PWA(TypeScript / xterm.js / Web Push / Service Worker / 状態管理) |
| E2EE | ペアリング時鍵交換(QRに公開鍵)、libsodium。sessionId等の制御メタも暗号化 |

## 6. 機能要件(v0.3)

### FR-1 ペアリング・認証(フェーズ1着手)
- FR-1.1 ワンタイムのペアリングQR/URL(有効期限付き)を拡張が発行
- FR-1.2 ペアリング時に鍵交換、以後の全通信(制御メタ含む)をE2EE
- FR-1.3 ペアリング済みデバイス一覧・個別失効(revoke)
- FR-1.4 全リモート接続を即時遮断するキルスイッチ

### FR-2 ホスト型 pty セッション(マルチ対応)
- FR-2.1 リモートから新規 pty セッション作成(起動は拡張設定のプリセットのみ)
- FR-2.2 入出力をリアルタイム双方向中継(体感1秒未満)
- FR-2.3 許可プロンプトにスマホから応答
- FR-2.4 切断・再接続でセッション維持+scrollback 再送
- FR-2.5 IDE側ターミナルでも同一セッションを閲覧
- **FR-2.6 複数の pty セッションを同時にホストし、各々が独立して動作(バックグラウンドも実行継続)**
- **FR-2.7 セッションごとに sessionId で入出力を多重化。1本のリレー接続で全セッションを収容**

### FR-3 セッション一覧・切替(v0.3 新設)
- FR-3.1 ホストは全セッション(pty + agent)のメタデータ一覧をクライアントに同期
- FR-3.2 クライアントは一覧を表示し、任意のセッションを選んで購読・操作できる
- FR-3.3 セッションの status(running/waiting-input/idle/exited)を一覧に反映
- FR-3.4 pty セッションの終了・agent 会話の選択解除ができる

### FR-4 Agent Manager 会話ミラー(read-only)
- FR-4.1 会話DBを監視し新規ステップを該当 agent セッションに差分配信
- FR-4.2 発言種別(ユーザー/モデル/ツール/サマリ)を区別表示
- FR-4.3 抽出失敗は劣化表示、機能全体は落とさない
- FR-4.4 各 agent 会話を独立したセッションとして一覧に出す

### FR-5 通知(Web Push)
- FR-5.1 いずれかの pty セッションが入力待ちになったら通知(どのセッションかを含む)
- FR-5.2 いずれかの agent 会話に新規ステップが出たら通知(オン/オフ可)

### FR-6 Agent Manager 操作(実験的・既定オフ)
- FR-6.1 既定オフの実験フラグ。有効化はホスト側の明示操作を要する
- FR-6.2 内部コマンド経由でプロンプト送信(`antigravity.sendPromptToAgentPanel` 等)
- FR-6.3 内部コマンド経由で承認・却下(`antigravity.command.accept` / `.reject` 等)
- FR-6.4 対応コマンドが無い/失敗時は明確にエラー、他機能に波及させない
- FR-6.5 リモート操作は監査ログ+レート制限

### FR-7 一般公開・運用
- FR-7.1 Open VSX で拡張公開
- FR-7.2 リレーはマルチテナント、テナント間は暗号レベルで分離
- FR-7.3 匿名利用を基本(課金導入時に再検討)
- FR-7.4 利用規約・プライバシーポリシー。B/C が非公式であることを明記

## 7. 非機能要件(v0.3)

| # | 要件 |
|---|---|
| NFR-1 | E2EE必須。リレーに平文を置かない。ホストはアウトバウンドのみ |
| NFR-2 | リモートに与える能力を最小化。pty は起動プリセット制、agent 操作は既定オフ・監査ログ・レート制限 |
| NFR-3 | リレー障害時もローカル作業は無影響 |
| NFR-4 | 会話DBの外部送信はミラー/操作を明示有効化時のみ。既定オフ |
| NFR-5 | ホスト常駐処理は Antigravity 動作を阻害しない |
| NFR-6 | 個人開発で維持可能なリレー運用費 |
| NFR-7 | 内部コマンド/DB依存部はバージョン耐性(機能検出してから使う) |
| **NFR-8** | **マルチセッションのスケール: 1ホストで最低8セッション同時を目標。1セッションの高負荷出力が他セッションの応答性を著しく損なわない(出力のバックプレッシャ/レート制御)** |

## 8. リスクと対応(v0.3 追加分)

| リスク | 影響 | 対応 |
|---|---|---|
| 多数セッションの同時出力でリレー帯域/クライアント描画が飽和 | 中 | セッション単位のレート制御・非表示セッションは出力を間引き/バッファ(NFR-8) |
| sessionId 詐称による別セッションへの混線 | 中 | E2EE 内での sessionId 検証、ホスト側で所有権チェック |
| (既存)DBスキーマ/内部コマンド変更で B・C 破損 | 中 | ベストエフォート/実験扱い、機能検出 |
| (既存)リモート承認開放で攻撃面拡大 | 高 | FR-6 既定オフ・監査・レート制限 |
